# Database Design

**Status:** Phases 0–3 implemented as three migrations (`foundation`, `master_data`, `inventory_engine`). Prisma is the source of truth; this document records the design decisions and constraints.

## Conventions

- **PKs:** UUID v4 generated by Prisma client (`@default(uuid())`).
- **Timestamps:** `created_at`/`updated_at` as `timestamptz(6)`; `@updatedAt` maintained by Prisma.
- **Money:** `Decimal(18,2)` for amounts (balances, limits), `Decimal(18,4)` for rates/prices (purchaseRate, MRP — paise precision plus GST rounding headroom). Never floats.
- **Quantities:** `Decimal(14,3)` (strips, ml).
- **Tenancy:** every tenant-owned table carries `organizationId` with an index; composites begin with `organizationId`. Branch/warehouse scoping is explicit per table where relevant.
- **Enums:** Postgres enums for statuses (Users, Batches, Movements, Transfers, Counts, Vendors, Customers, Products).

## Critical uniqueness constraints

| Table | Constraint | Rationale |
|---|---|---|
| users | `email` | global identity |
| organizations | `slug` | URL-safe identity |
| organization_memberships | `(organizationId, userId)` | one membership per user per org |
| user_branch_assignments | `(membershipId, branchId)` | no duplicate assignment |
| roles | `(organizationId, name)` | role names unique per org (system templates seeded at registration) |
| branches | `(organizationId, code)` | branch codes unique within org |
| products | `(organizationId, sku)` | SKU unique per org |
| product_barcodes | `(productId, barcode)` + index on barcode | multi-barcode support, POS lookup |
| tax_rate_versions | index `(organizationId, hsnCode, effectiveFrom)` | versioned resolution, never unique — history kept |
| inventory_batches | `(organizationId, productId, warehouseId, batchNumber, expiryDate)` | same lot received twice merges; different expiry = different batch |
| inventory_balances | `(batchId, warehouseId)` | one balance row per batch per warehouse |
| document_number_sequences | `(organizationId, scope, fiscalYear, prefix)` | server-controlled numbering with FOR UPDATE |
| stock_count_lines | `(countId, batchId)`; stock_transfer_lines `(transferId, batchId)` | one line per batch per document |

## Append-only tables

`audit_logs`, `inventory_movements`, `product_change_history`, `subscription_events` are append-only by service convention (no update/delete code paths). Production hardening (Phase 12) adds `REVOKE UPDATE, DELETE` grants for the application role — documented in [security-model.md](security-model.md) as an outstanding step.

## Balance vs ledger

`inventory_balances` is a transactionally-maintained projection of `inventory_movements` (the source of truth). Every balance mutation happens inside the same transaction as its movement insert, under `SELECT ... FOR UPDATE` on the balance row. `/api/v1/inventory/reconcile` recomputes Σ movements per (batch, warehouse) and reports mismatches; an integration test asserts consistency after adjustments, transfers, and count postings.

## Transaction boundaries (summary)

- Batch creation (+opening stock): one transaction — batch upsert + balance delta + movement.
- Stock adjustment: one transaction — balance delta + movement, then adjustment record + audit.
- Transfer dispatch: one transaction — transfer + lines + per-line balance deduction with eligibility checks.
- Transfer receipt: one transaction — per-line receipt, destination batch upsert, `TRANSFER_IN` movements, over-receipt rejection (rolls back whole receipt).
- Count posting: one transaction — all variance movements + status flip.
- Registration: one transaction — user + org + roles + membership + trial subscription + branch + settings; audit written **after commit** (separate connection; writing inside would race the uncommitted FK target).

Full boundary catalogue: [transaction-boundaries.md](transaction-boundaries.md).

## Known limitations (honest)

- Row-level security (Postgres RLS) is **not** enabled — the application layer enforces tenancy and is covered by negative tests; RLS is planned with the pooling model decision in Phase 12 (spec §5 leaves this open).
- `stock_reservations` exists but is unused until POS carts (Phase 5) create reservations.
- Opening-balance columns on vendors/customers are stored but not yet posted to a ledger — accounting (Phase 7) will realize them.
- Billing counters are modelled but unused until POS (Phase 5).
